# context_signer_module: design

**Status:** draft, 2026-10-24.
**Requirements:** Muster's `docs/design/wallet-signer-spec.md` (corpetty/muster `c47cda4`), "the
spec" below.
**Built on:**
- `logos.signer/1` (logos-co/logos-signer-interface `03eece5`);
- `signer_manager_module` (`d2548c6`);
- `keystore_module` (`127d4ac`; Basecamp 0.3.2 still ships `2318c679`).

## 1. Where this sits

The platform already has the aggregator the spec asks for (spec §7.1). `signer_manager_module`
does most of the work:
- it takes signature requests from any named module, with keystore_module's approval API;
- it renders each request through the Signer app, computes every digest, and checks every
  signature against public material before release;
- it holds the unlock terms (`ttlMs`, `count`, `apps`, confirm or "without asking") that the spec
  calls standing grants;
- it routes signing to signers behind `logos.signer/1`: the keystore, Keycard, Keycard Shell, QR,
  and Ledger and Trezor modules.

Its families are `evm`, `bitcoin` and `bitcoin_taproot`.

**This module is one more signer behind that interface,** for the families no other signer holds.
It is not a second aggregator and has no approval contract of its own. An earlier draft of one is
parked on the branch `parked/own-approval-contract`.

## 2. What it is

A Rust cdylib Logos module (`type: core`). It is a leaf: no network, and no calls out.

**Families today:** `ed25519`, an identity key, through the interface branch
`feat/ed25519-family` (`docs/proposal-logos-signer.md` §1).

**Callers:**

| Methods | Admits |
|---|---|
| `signer_info` | anyone |
| `signer_accounts`, `unlocked` | the manager or the custodian |
| `sign`, `sign_status`, `sign_result`, `cancel_sign`, `unlock`, `lock` | the manager (default `signer_manager_module`) |
| `create_mnemonic`, `import_mnemonic`, `derive_account`, `forget_group` | the custodian (the keys app) |

These are keystore_module's tiers, attested by `current_caller()`.

**Signing.** Signing is keystore_module's signer half:
- hashes only;
- every item is checked before the vault opens;
- a password per request, or an unlock;
- `wrong_secret` / `locked`;
- a job finishes inside `sign`.

## 3. The core (`rust-lib/src`, no Logos runtime)

| Module | Holds | Held to |
|---|---|---|
| `record` | The strict decoder and encoder for Muster's `[domain, {fields}]` records (spec rule 2, invariant 5) | Muster's CDE subset; non-canonical, float, tag and indefinite encodings refused |
| `derive` | A key per `(scheme, purpose, context)`: `m/7432'/scheme'/c0'…c7'`, hardened, the `c`s from a hash of purpose and context; BIP-32 for secp256k1, SLIP-0010 for Ed25519; the master fingerprint (spec §3.1, rules 7–8) | BIP-32 and SLIP-0010 vector 1 |
| `identity` | Ed25519, the X25519 key libsodium derives from it, sealed-box open, and the HMAC derived secret (spec §3.2) | `tests/vectors/libsodium.json`, generated by libsodium itself (`tools/gen_libsodium_vectors.py`) |
| `vault` | The seed as a Web3 Secure Storage (scrypt) vault; the public key index; group fingerprints | the BIP-39 seed vector; atomic writes |
| `signer` | `logos.signer/1` over the vault, with `unlock`, `lock` and `derive_account` | the interface's conformance suite; `tests/signer.rs` |

## 4. What Muster gets, and what waits on upstream

| Spec need | Status |
|---|---|
| Ed25519 authorship signatures (spec §3.2) | **Here**, behind the manager, once the manager takes `ed25519` and a `record` kind (proposal §1, §2a) |
| Same key after a restore (spec §6 recovery) | **Here**: tested across two vaults from one phrase |
| Fresh key per room (rule 8) | **Here**, by the custodian's `derive_account`. An app asking for one waits on proposal §2b |
| No prompt per message (spec §3.2) | `unlock` is here; the manager routing an unlock to this signer waits on proposal §2c |
| X25519 open, the derived secret | in the core (`identity`), with **no contract method**: outside `logos.signer/1`'s rule (proposal §2d) |
| LEZ BIP-340 messages, FROST | later (proposal §3) |
